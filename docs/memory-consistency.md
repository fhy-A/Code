# 持久记忆的一致性与授权

记忆正文仍使用原来的 Markdown / frontmatter；`MEMORY.md` 是从正文重建的索引，不是事实源。`MEMORY_DIR` 同时决定正文、索引与辅助状态的根目录，旧的 `MEMORY_INDEX_PATH` 常量不再决定实际写入位置。因此只隔离 `MEMORY_DIR` 的测试也不会写到另一个目录的索引。

## 保存、重命名与恢复

设置页、`save_memory`、受管理目录中的 `write_file` / 编辑提案 / `delete_file` 共用 `code_runtime/managed_memory.py`。普通文件工具先执行原有路径解析，不增加可访问路径；记忆入口再拒绝保留索引、内部辅助文件、链接与目录联接。模型保存不把已有记忆重新归属到另一个项目；同名冲突需要选择新名称。

每个目录通过线程锁与 `.memory.lock` 协调受管理操作。`.memory-transaction.json` 保存本次变更前的正文和预期变更摘要；正文与索引完成后才写入 `.memory-receipts` 下的操作回执并清理日志。失败会尝试还原原正文并重建索引；进程中断后，下一次访问先恢复未完成事务。恢复中发现外部变更或损坏的辅助记录时停止，不覆盖冲突正文。幂等返回也修复索引；已完成操作的目标后来被修改或重建时，旧回执返回冲突并明确没有再次应用。

重命名使用单次 `POST /api/memory`：`originalName`、新 `name`、`revision`、`scope`、`operationId` 和正文在同一事务内处理。新名称已存在时拒绝覆盖；保留原有项目、创建时间和未知元数据。文件名保留原来的 ASCII slug 边界，`MEMORY` 及 Windows 设备名不可作为正文名称。与保留索引仅大小写不同的旧文件会明确报冲突，不静默隐藏或覆盖。

这套机制协调经过上述入口的操作。原有自动模式的任意命令执行、外部编辑器和直接文件系统操作并未变成受管理事务，也未获得新权限；不能把版本检查描述成对任意外部写者的文件系统强隔离。

## 删除确认

`delete_memory` 参数只有确切名称和作用域：`legacy`、`global` 或 `project:<原始项目路径>`。服务端读取当前文件版本，将名称、作用域和版本冻结到授权请求及对应工具执行记录中；真实授权提交必须匹配该请求 ID。模型填写的 `confirmed` 或内部字段不能授予删除权限，`save_memory` 的后台写入能力也不授予删除权限。

主运行的接受编辑和自动模式均需这次确认；后台或子运行不能使用专用删除工具。普通 `delete_file` 命中记忆正文时也走同一确认与版本检查。用户点击设置页确认时提交列表中对应的版本和作用域；版本变化需刷新后重新确认。恢复、重试或旧回执均不能授权删除后来重建的同名记忆。

## 请求上下文与旧运行

新前端在 AgentRun 创建参数中发送 `memoryContextVersion: 1`，不把记忆正文拼入冻结的系统提示词。该可选合同字段随 Run 保存与恢复，不发送给模型供应商。服务端根据 Run 固定的 `cwd`，在每个模型请求（包括压缩请求）组装时读取当前正文，加入独立的请求消息。浏览器缓存只供界面提示，使用项目、导航序号和请求序号防止旧响应覆盖新结果。当前会话和当前项目前台运行的受管记忆工具完成后，立即失效旧正文和数量并触发一次读取；旧会话、后台或其他项目事件不投影到当前界面，不新增轮询。

前后端需同步生效；只更新服务但保留旧页面会继续生成旧内联提示词，不能通过重复发送新消息绕过门禁。每条可见记忆同时携带名称和确切 scope 元数据，模型可以直接使用，不必猜测或先试错。

项目过滤保持原有含义：没有项目字段的旧记忆、`project: *` 和当前项目记忆可见；当前项目为空时仍保留旧版的全部可见行为。已发送的请求、历史消息、工具结果和已有摘要不回写、不追溯清除。

缺少新合同且系统指令包含旧生产者的精确内联记忆标记时，在下一次模型出站边界进入不可恢复的 `waiting_recovery`，错误码为 `memory_context_new_turn_required`。界面提示确认服务已更新并刷新页面加载匹配的新前端后，再在同一会话发送新消息开启新轮次；旧 Run 和历史保留。不猜测截取旧提示词，不后台扫描旧 Run；没有内联标记的旧 Run 和采用新合同的 Run 不受此门禁影响。

## 回退与验证范围

正文格式没有迁移。代码回退前应停止本阶段创建的活动运行，并在当前实现下完成未结束事务的恢复；不得删除待恢复日志来掩盖失败。回退后在原会话开启新轮次，不用旧实现继续新合同的活动运行。辅助锁和已完成回执不承担正文事实，旧实现忽略它们也不等于完成待恢复事务。

`consolidate-memory` 负责内容取舍与整理，程序负责索引一致性。本阶段不执行或改写该 Skill；其旧说明中的直接写索引步骤会受到保留索引保护，应改为检查程序生成的索引后再单独验收，不据此宣称完整整理流程通过。

专项入口是 `tests/test_memory_consistency.py` 与 `tests/e2e/h4/code084-memory.cjs`。普通测试入口不导入服务，由它创建临时 `CODE_DATA_DIR` 并在受控子进程执行 `tests/memory_consistency_cases.py`；未设置该环境的常规收集仍可执行；UI 验收使用自建隔离服务和浏览器，检查 bundle / classic、设置页 CRUD、语言切换、缓存乱序、窄屏确认按钮与进程、端口和临时根清理。它们不读取真实记忆或调用真实模型。
