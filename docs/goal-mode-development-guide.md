# Code Goal 复杂长任务规划、执行与验收开发指导

> 状态：产品与工程指导已确认，功能尚未实现。本文是 Code 后续 Goal 功能开发的规范性依据；涉及产品行为的实现若与早期规划冲突，以本文为准。

## 一、文档目的与边界

Goal 要解决的不是“增加一个斜杠命令”，而是把一次性对话升级为可恢复、可持续执行、可验收的持久任务契约：

1. 用户与系统先明确目标、约束、计划和完成条件；
2. 一轮模型响应结束后，只要目标尚未完成且仍能安全推进，系统可以启动新的 AgentRun 继续当前任务；
3. 每一步必须以可复核证据满足验收条件，不能仅凭模型口头自报完成；
4. 无法安全推进时停止自动续跑，保留当前阶段并向用户说明所需输入；
5. Goal 不扩大文件、命令、网络、授权或发布权限，既有安全边界始终优先。

本文固化产品决策、数据与执行边界、阶段路线和验收口径，不规定尚未验证的具体存储格式、内部工具名称或调度算法。

## 二、官方参考与本项目决策的区分

### 2.1 可确认的官方产品事实与启发

本文只参考以下官方页面：

- [Follow goals](https://learn.chatgpt.com/use-cases/follow-goals)：将 Goal 描述为跨多轮持续推进、直到满足可验证停止条件的持久目标，并强调目标、非目标、验证方式和停止条件。
- [Long-running work](https://learn.chatgpt.com/docs/long-running-work)：建议先明确结果、约束和完成定义，在同一任务中保留上下文；目标不清晰时先用 `/plan`，再用 `/goal` 执行，并可通过后续消息补充上下文、调整约束或询问状态。
- [Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)：公开说明 `/plan` 用于进入计划模式并形成执行计划，`/goal` 用于创建或查看长期目标；官方产品还提供若干 Goal 管理命令。

这些页面提供的是产品启发和公开交互事实。本文不把官方未公开的内部状态机、token 预算、工具协议、自动续跑算法或持久化结构写成事实。

### 2.2 Code 的规范性产品决策

Code 不照搬官方产品的全部命令和控制界面。本文确认的本项目差异是：

- `/goal` 是显式创建与状态查看入口，但普通自然语言同样可以触发 Goal 建议或创建；
- Goal 启动后的补充、暂停、恢复、修改和清除以普通消息为主要控制面；
- UI 只投影计划步骤、当前阶段和完成情况，不建设任务管理控制台；
- 顶层计划严格使用三态，执行阻塞、失败、重试和等待用户均留在内部运行信号中；
- `/plan` 负责澄清目标、约束与验收，`/goal` 负责持久执行闭环。

以上是 Code 的产品选择，不代表官方 Codex 的内部实现。

## 三、用户体验与产品契约

### 3.1 用户如何使用

典型流程如下：

1. 用户用普通消息描述复杂任务，或通过 `/goal` 明确创建 Goal；
2. 目标或验收条件不清楚时，先用 `/plan` 澄清；
3. 系统生成通常为 3～8 个产品级步骤的计划，并为每步建立内部验收条件；
4. 用户确认后开始执行；只有用户显式要求自动开始时，才可跳过单独的开始确认；
5. 系统用一个或多个既有 AgentRun 推进当前步骤，一轮结束但仍可安全推进时自动续跑；
6. 用户随时用普通消息补充条件、询问状态、暂停、恢复、修改或清除目标；
7. 所有步骤均有充分证据后，Goal 完成并停止自动续跑，计划作为历史保留。

Goal 完成后，后续普通消息不得静默重启它。新的复杂任务应创建新的 Goal。

### 3.2 最小 UI

Goal UI 只展示：

- 整体任务的步骤及每步描述；
- 当前阶段；
- 每一步是未开始、进行中还是已完成。

UI 不提供编辑、暂停、恢复或清除按钮，也不展示预算、耗时、阻塞原因、失败详情或其他 Goal 元数据。上述控制和说明仍通过对话完成。系统级“立即停止”继续作为应急安全能力存在，但不是 Goal 管理按钮。

### 3.3 `/plan` 与 `/goal` 的分工

| 入口 | 主要职责 | 产物 |
|---|---|---|
| `/plan` | 澄清目标、范围、约束、风险和验收条件 | 可确认的执行方案 |
| `/goal` | 创建或查看持久目标，并进入跨 AgentRun 的执行闭环 | 持久 Goal 与计划投影 |
| 普通消息 | 补充上下文、控制执行、调整计划或询问状态 | 必要时产生新的 Goal revision |

普通 prompt 不应被本地命令解析器误判为斜杠命令；显式 `/goal` 必须由确定性命令入口处理，不能依赖模型猜测控制语义。

## 四、计划模型与三态规则

### 4.1 顶层步骤状态

公开计划步骤严格只有以下三种状态：

| 状态 | 含义 |
|---|---|
| `pending` | 尚未开始 |
| `in_progress` | 当前正在推进，或正等待继续推进所需的条件 |
| `completed` | 验收条件已经被证据满足 |

同一时间最多一个顶层步骤为 `in_progress`。并行子任务属于当前顶层步骤的内部执行，不得投影成多个同时进行的顶层步骤。

`blocked`、`failed`、`retry`、`waiting_user` 等词只表示内部执行事件或运行信号；它们不会成为第四或第五种计划状态。无法继续时，当前顶层步骤仍保持 `in_progress`。

### 4.2 步骤粒度与变更

- 计划通常保持 3～8 个产品级步骤；实现细节、单条测试命令、一次工具调用和重试不膨胀为顶层步骤。
- 模型可以增删或重排尚未开始的步骤，但只有有意义的计划变化才增加 `revision`。
- 已完成步骤不得静默消失，也不得在新计划中被悄悄改写成从未发生。
- 新要求使已完成结果失效时，必须明确将该步骤重新打开为 `in_progress`，或新增返工步骤，并向用户说明原因。
- 明显扩大目标范围、改变完成或验收标准、放弃已经验收的结果、改变安全或授权权限边界，必须先取得用户明确确认。

## 五、普通消息驱动的控制

运行中的每条用户消息至少按以下意图分类：

| 意图 | 处理原则 | 是否通常增加 revision |
|---|---|---|
| 上下文补充 | 纳入当前步骤上下文，不自动改计划 | 否 |
| 约束更新 | 评估对未完成步骤和验收条件的影响 | 有实质影响时是 |
| 计划调整 | 增删、重排 pending 步骤，或显式返工 | 是 |
| 暂停 / 恢复 | 改变是否允许启动后续 AgentRun，不改变三态计划 | 否 |
| 目标替换 / 取消 | 先确认重大变化，再结束当前 Goal 或创建新 Goal | 是 |
| 状态询问 | 返回当前步骤、证据和下一动作 | 否 |
| 无关旁支 | 作为普通对话处理，不污染 Goal | 否 |

意图判断可以由模型提出，但服务端 reducer 必须确定性校验可执行的状态迁移、revision 和所有权。目标替换、取消或重大边界变化不得仅凭含糊文本静默生效。

## 六、验收与证据

### 6.1 每步的内部验收契约

每个步骤内部至少包含：

- 验收条件；
- 预期证据类型；
- 已收集证据及来源；
- 证据的时间、关联 AgentRun 和适用范围；
- 仍未满足的条件。

AgentRun 成功结束只说明一次运行完成，不等于步骤完成。服务端 reducer 只有在所需证据齐备且仍适用于当前 revision 时，才允许把步骤改为 `completed`。

### 6.2 证据分层

| 类型 | 例子 | 完成门禁 |
|---|---|---|
| 机器可验证 | 测试退出码、Git 白名单、构建哈希、API 状态 | 校验规则通过后可自动接受 |
| Agent 报告 | 根因说明、影响范围、文档核对 | 只能作为辅助证据，不能单独覆盖客观门禁 |
| 用户人工证据 | UI 视觉、手感、业务可用性、外部人工结果 | 必须等待用户明确 PASS |

最终 Goal 只有在全部步骤完成后才可结束。任何主观 UI 或业务验收仍待用户确认时，系统只能说明“等待验收”，不能因模型声称完成而关闭 Goal。

## 七、推荐架构

### 7.1 复用现有执行基础

Goal 应建立在现有 AgentRun、Child AgentRun、Session JSONL / 事件流和前端投影之上：

- Goal 是跨多个 AgentRun 的持久编排对象；
- 一个 AgentRun 只承担有限的一轮或一个执行片段，不通过无限延长单个 run 实现长任务；
- Child AgentRun 和既有并发槽位可服务于当前顶层步骤的内部并行；
- Goal reducer 消费确定性事件，更新当前步骤、证据和续跑决策；
- 浏览器只显示服务端投影，不作为 Goal 的事实源或写入者。

### 7.2 建议的数据模型

内部对象可以包含：

- `goal_id`、`session_id`、`objective`、`revision`；
- `steps`、`current_step_id`；
- 每步的验收条件、证据、关联 AgentRun 和内部尝试记录；
- `waiting_user` 与其他 runtime signals；
- 创建、更新、开始、完成和最近续跑时间；
- 当前写入者、幂等键和恢复游标。

公开的 `steps[].status` 只能使用 `pending`、`in_progress`、`completed`。等待、阻塞、失败、重试、取消请求和预算停止均属于内部 runtime signals 或事件，不得混入计划状态或直接投影为额外状态。

MVP 每个 Session 最多一个 active Goal。多个 AgentRun 可以先后服务同一 Goal，但同一 Goal 的状态更新必须经过单一服务端写入者和 revision 校验。

### 7.3 状态更新职责

- **模型可建议**：目标摘要、计划内容、未开始步骤调整、验收候选、证据解释和下一动作。
- **服务端 reducer 决定**：Goal 创建与唯一性、revision、当前步骤、证据关联、三态迁移、幂等续跑、暂停状态和终止条件。
- **用户必须确认**：重大范围或验收变化、放弃既有验收结果、权限边界变化，以及所有主观验收。

模型工具的名称和精确协议仍需在实现阶段验证。无论最终采用 `create_goal` / `get_goal` / `update_goal`，还是更窄的提议与报告工具，都必须使用 revision、幂等键、字段白名单和拒绝条件，不能允许模型直接覆盖整个持久对象。

## 八、自动续跑与无进展保护

一次 AgentRun 结束后，Goal 编排器按以下顺序决定是否续跑：

1. 重新读取最新 Goal revision、当前步骤和权限现场；
2. 归档本轮新证据，判断验收条件是否满足；
3. 若当前步骤完成，确定性推进到下一个 pending 步骤；
4. 若仍有安全、明确且获授权的下一动作，创建新的 AgentRun；
5. 若缺少用户输入、权限、外部状态或可行路径，停止本轮自动续跑。

不得用无限循环、无界重试或持续消耗来掩盖停滞。系统需要识别无进展，例如连续运行没有新增证据、重复相同失败、下一动作不再明确或需要新的授权。每类问题只允许有限的替代尝试；达到界限后，当前步骤保持 `in_progress`，并向用户说明：

- 卡在哪里；
- 已尝试什么；
- 为什么不能安全继续；
- 需要用户提供什么。

用户回复后从同一步恢复。时间或 token 预算如后续引入，只能作为暂停或停止续跑的条件，不能被当作完成条件。

## 九、恢复、幂等与不可逆动作

### 9.1 刷新与完整重启

Goal、步骤、证据、revision、等待信号和续跑归属必须由服务端持久化。页面刷新只重建投影；服务完整重启后应通过持久事件和恢复游标判断：

- 哪个 Goal 仍处于活动状态；
- 当前步骤及最后一条已接受证据；
- 是否已有 AgentRun 在运行或等待授权；
- 是否允许创建新的续跑 AgentRun。

恢复不能依赖浏览器内存，也不能因连接丢失自动重复请求。

### 9.2 不可逆动作

提交、发布、迁移、删除和线上配置等动作必须至少具备：

- 稳定幂等键；
- 执行前现场核对；
- 明确授权证据；
- 执行后的可验证完成证据；
- 恢复时先查证结果、再决定是否继续。

Goal 的“仍未完成”绝不等于授权重复不可逆动作。无法确认外部结果时必须等待用户或安全的外部核对。

## 十、权限、安全、并发与单写入者

- Goal 不扩大当前权限。文件写入、命令、网络、授权、发布、删除和线上配置继续遵守项目现有边界。
- 自动续跑只能执行当前已获授权且在既定范围内的下一动作；新权限需求必须回到现有授权流程。
- 同一 Session 的 MVP 只允许一个 active Goal；Goal reducer 是唯一状态写入者。
- Child AgentRun 或后台 run 只能报告内部结果和证据候选，不能直接推进顶层步骤或宣布 Goal 完成。
- 并行任务必须受现有并发上限约束；涉及同一文件或同一外部资源的写操作应串行化或使用明确冲突检测。
- revision 不匹配、所有者不一致、证据来源不明、Goal 已完成或已取消时，更新请求必须被拒绝。
- 紧急停止可终止当前运行，但不能伪造步骤完成；恢复后仍需根据持久事实重新判定。

## 十一、持久化、兼容与回退

推荐将 Goal 作为服务端拥有的版本化事件与快照，由 Session 关联并通过既有事件流投影；不要把前端 state 或单个 AgentRun snapshot 当成唯一事实源。确切采用 Session JSONL 扩展、独立 Goal 日志或二者组合，应在实现阶段通过原子性、单写入者和损坏恢复验证后确定。

兼容要求：

- 旧会话没有 Goal 数据时，普通对话、AgentRun 和会话读取行为完全不变；
- 新事件必须可被旧数据读取路径忽略或安全降级；
- bundle 与 direct classic 使用同一服务端事实源和投影契约；
- 刷新与完整服务重启不得重复续跑或不可逆动作；
- Goal 数据缺失、版本未知或局部损坏时，停止自动续跑并保留会话，不得让损坏扩散到 Session JSONL；
- 关闭 Goal 功能开关后，应退回普通单轮执行，既有会话消息仍可读取。

回退实现时应优先撤销独立阶段提交和关闭功能开关，而不是迁移或删除历史会话数据。

## 十二、分阶段开发路线

### 阶段 1：MVP 持久闭环

目标：一个 Session 一个 active Goal，形成创建、确认、执行、续跑、证据验收、等待用户和完成历史的最小闭环。

建议范围：

- 本地 `/goal` 解析和普通消息意图接入；
- Goal 服务端模型、reducer、事件持久化与 Session 关联；
- AgentRun 结束后的有限自动续跑；
- 三态计划投影和最小 UI；
- 机器证据与用户 PASS 门禁；
- 刷新、完整重启、幂等恢复与安全降级。

MVP 明确不做：多 active Goal、可视化任务管理控制台、UI 编辑/暂停/恢复/清除按钮、预算或耗时展示、拖拽编排、跨 Session Goal、复杂优先级、自动发布权限、通用 Workflow、无界重试和滚动位置等无关持久化。

建议拆成独立提交：数据与 reducer、命令/消息入口、续跑与恢复、最小 UI、验收与兼容门禁。每个阶段都必须能单独回退。

### 阶段 2：恢复与并行增强

目标：在 MVP 稳定后，增强多 AgentRun 编排、当前步骤内并行、冲突检测和更严格的重启恢复。

重点包括：

- Child AgentRun / detached run 的证据归属与去重；
- 单顶层步骤内的并行子任务和现有槽位复用；
- 无进展分类、有限替代策略和恢复游标；
- 写冲突、陈旧 revision、重复 completion 和不可逆动作恢复测试；
- bundle / direct classic 的投影一致性。

### 阶段 3：自动验收与高级控制

目标：在证据模型稳定后，增加可配置的机器验收、受控预算停止条件和更强的审计能力。

可评估内容：

- 版本化验收器与证据策略；
- token / 时间 / run 数预算作为停止条件；
- 更细的审计、导出和运维诊断；
- 经单独安全设计后的跨会话或 Workflow 集成。

高级能力不得改变三态 UI、消息驱动控制和用户主观验收门禁。

## 十三、验收矩阵

### 13.1 自动验收

| 场景 | 可观察标准 |
|---|---|
| 创建与唯一性 | 同一 Session 不会出现两个 active Goal；重复请求按幂等键复用 |
| 三态迁移 | 顶层步骤只出现三种状态，且最多一个 `in_progress` |
| 证据门禁 | AgentRun 自报成功但证据不足时，步骤不会完成 |
| 自动续跑 | 有安全下一动作时创建新 AgentRun；无进展或缺输入时停止创建 |
| 消息控制 | 状态询问不增加 revision；实质计划变化才增加 revision |
| 并发隔离 | 子任务只更新当前步骤的内部证据，不污染其他 Goal 或 Session |
| 刷新恢复 | 刷新只重建投影，不重复 AgentRun 或不可逆动作 |
| 服务重启 | 从持久事实恢复当前步骤、证据和等待现场，无法判定时安全停止 |
| 兼容降级 | 无 Goal 的旧会话行为不变；损坏 Goal 不破坏会话读取 |
| 权限拒绝 | Goal 不能绕过现有授权、发布、删除或线上配置门禁 |

### 13.2 人工验收

| 场景 | PASS 标准 |
|---|---|
| 复杂任务创建 | 用户能看懂 3～8 个步骤、当前阶段和完成情况 |
| 消息补充与状态询问 | 普通消息自然生效，不要求记忆繁琐子命令 |
| 暂停与恢复 | 对话指令停止或恢复后续 run，计划步骤不出现额外状态 |
| 计划调整 | pending 步骤可调整，completed 步骤不会静默消失 |
| 等待用户 | 系统清楚说明阻塞点、已尝试内容和所需输入，不无限续跑 |
| 主观验收 | UI 或业务步骤在用户明确 PASS 前不会完成 |
| Goal 完成 | 完成后停止自动续跑，计划保留；普通后续消息不会静默重启 |
| 明暗与双入口 | bundle / direct classic 均能看到一致、可访问的最小计划投影 |

## 十四、实现前仍需验证的问题

以下是工程实现问题，不重新打开本文已确认的产品决策：

1. Goal 事件与快照最终采用 Session JSONL 扩展、独立日志，还是带引用的组合存储；
2. reducer 事件版本、原子写入和损坏恢复的具体格式；
3. 模型工具采用通用 Goal 更新接口还是更窄的提议、证据报告接口；
4. “有限替代尝试”和无进展检测的分类、默认上限与可测试规则；
5. 自然语言 Goal 意图分类的置信门槛，以及重大变化的确定性确认协议。

这些问题必须通过现有实现核对、协议设计和恢复测试决定，不能从官方未公开行为推断。

## 十五、开发执行准则

开始每个 Goal 实现阶段前，应先完成只读现状分析和用户方案确认；实施时使用精确文件白名单，分离数据模型、执行编排、前端投影和验收测试。任何需要扩大权限、改变会话兼容、增加持久化迁移或修改三态与消息驱动产品决策的发现，都必须暂停并重新确认。

本文落盘不表示 `/goal`、Goal 工具、自动续跑、持久化 reducer 或 UI 已经实现。
