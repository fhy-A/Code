# 同轮引导协议

## 目标与阶段边界

运行中的后续用户消息需要能够进入当前 AgentRun，而不是只能等待当前任务完成后创建新一轮。阶段一只建立服务端与前端运行时客户端可调用的同轮引导协议；它不改变现有输入框行为，也不增加用户可见的“引导”“排队”状态。

后续阶段才把前端默认跟进行为切换为引导，并保留显式排队入口。无论采用哪一种运行语义，消息都继续按普通用户消息渲染；差异只存在于调度与模型上下文边界。

## 协议与持久化

- `POST /api/agent/runs/{agentRunId}/steer` 接收一条用户消息和可选 `clientRequestId`。
- 同一个 `clientRequestId` 与同一内容重复提交返回原回执；同一 ID 携带不同内容会被拒绝。
- 活动 Run 最多保留 32 条尚未消费的引导，终态 Run 返回冲突，不静默创建新 Run。
- AgentRun 记录升级为 v4，新增 `pendingSteers` 与 `steerReceipts`；旧 v1～v3 记录加载时按空引导状态恢复，无需迁移原文件。
- 引导只在下一次模型边界原子消费一次。若引导在完成提交前到达，当前 Run 不进入终态，而是继续下一模型轮。
- 服务重启后，尚未消费的引导仍保留；恢复运行后只注入一次。

公开快照只返回待处理数量和不含正文的回执元数据。耐久事件 `steer_submitted` 与 `steer_consumed` 只记录 ID、状态和数量，不写入用户消息正文。用户正文仍只存在于受现有会话与 AgentRun 数据边界保护的消息记录中。

## 兼容与回退

- 会话 JSONL 格式未修改，旧消息展示不变。
- 旧 AgentRun v1～v3、经典前端和关闭新前端接线的场景继续沿用原有排队逻辑。
- 回退阶段一只需停止调用 `/steer` 并回退 v4 写入代码；已有 v4 记录的新增字段均为可选扩展，不影响旧字段读取。
- `steer_submitted / steer_consumed` 已纳入规范 reducer 与旧影子适配器，且不改变已有状态、轮次、工具或计时投影。

- 冻结投影契约补测：`23 passed, 164 subtests passed`。

- `npm run check:frontend`、Python/JavaScript 语法检查、Harness 兼容夹具和 `git diff --check` 通过。

## 后续验收

阶段二和阶段三仍需覆盖：运行中普通发送默认引导、显式排队、连续多条引导、图片消息、问卷/授权等待、刷新与服务重启、终态竞态、取消、后台任务和旧队列数据。必须确认引导与排队消息都没有额外前端提示，且引导不会丢失、重复注入或创建第二个 AgentRun。
