- **缺陷①选条与收口**：`_pending_update_handoff` 原先取「按文件名排序的第一条」，`Code-v0.6.10…` 永远排在 `Code-v0.6.11…` 之前，且从不持久化任何终态，于是同一提示每次启动重复出现。现改为按 **descriptor 版本语义**分类：运行版本 == journal 版本 → 收口 `installed`；journal 版本低于运行版本（已被取代）→ 收口 `failed` + `update_not_ready` + `retryable=False`；只有**严格高于**运行版本的 journal 才算待恢复交接，多个候选取**版本最大**者。收口**持久化写回该 journal**，只改已存在键的值，字段集合与其余字段含义不变（未新增字段、未新增状态值、未改 schema），并写旁路日志 `closeout=… persisted=…`。
- **缺陷②读不到 ≠ 不合格**：新增 `_read_pe_header_state` 与 `_read_windows_file_identity_detailed`（改用 `ctypes.WinDLL("version", use_last_error=True)` + `ctypes.get_last_error()`），把「读取失败」映射到新失败码 **`download_verify_unreadable`**（`retryable=True`，且**不在**不可重试集合内），把「读到但与 descriptor 不符」保留为 `download_pe_invalid`（不可重试、`reset_part`）。原 `_is_valid_windows_executable` / `_read_windows_file_identity` 保留为补丁点包装。不可重试集合抽为 `_UPDATE_INVALID_FILE_CODES` 并由 `_handle_restart` 使用；仍禁止在未通过校验时提供启动入口。
- **缺陷③假阴性取证**：`_UpdateFailure` 增加 `detail`，sidecar 日志新增 `detail=`（失败 API 与 Win32 错误码、`identity_mismatch version=… expected=…`）。`recover` 的 OSError 分支改为记 `verification_failed=download_verify_unreadable detail=…`。
- 隔离验证（真实代码路径，对话框与启动器用注入替身）：陈旧交接 → `_pending_update_handoff` 与 `_recover_pending_update_handoff` 均返回 `None`、**0 次弹窗、0 次启动**，journal 落盘为 `failed/completed/update_not_ready`；**再次运行仍 0 提示**；版本相同 → 落盘 `installed/installed`；两个候选 0.6.10 与 0.6.11（文件名序与版本序相反）→ 选中 **0.6.11**（旧实现会选 0.6.10）；更高版本合法候选 → 仍提供一次启动入口；`tests/test_server.py` **287 passed, 1 skipped, 50 subtests passed**（含既有下载/校验与恢复用例），恢复路径**八项控制 8/8** 复跑通过。

### v0.6.11 更新交接缺陷（v0.6.8 回归）修复：可诊断性、启动可见性与一次性过渡

- 根因（第一阶段已钉死）：v0.6.8（提交 `2de42d4`，2026-09-02「收口 DATA_DIR 单写者与更新器交棒」）把 v0.6.7 的纯 batch 更新器改写为 PowerShell + .bat 交接时丢掉三件事——先杀光同镜像进程的有界循环（v0.6.7 用 `tasklist | findstr /i Code-` + `taskkill /f` 最多 40×1 秒）、清理失败时的尽力而为语义、以及无条件 `start` 拉起新版本。结果：清理块 `Remove-Item` 删除正在运行的旧 EXE 抛 `System.UnauthorizedAccessException`（脚本第 203 行），被 `catch { $exitCode = 24 }` 静默吞掉，`.bat` 取到 24 即跳过启动并自删；09-08、09-11 两次更新因此失败，新版本永不启动、journal 停在 installing。A（PyInstaller Job 容器连带终止）已用同版本 onefile 实验否证（子进程存活 >17.5 秒、`IsProcessInJob=0`）。
- 修复（限定在更新交接路径与启动失败路径）：① PS 交接脚本新增阶段（wait-source／add-type／lock／replace／verify）与最终退出码落盘，`catch` 记录异常类型、消息与脚本行号，不再静默 exit；为不破坏既有 `Add-Content -LiteralPath $logPath` 的写入顺序契约，新增日志改用 `[System.IO.File]::AppendAllText`。② 尚未取得锁的阶段与失败证据写入 DATA_DIR 之外的手递日志 `<data>.code-update-handoff.log`，保持「未持锁不写 DATA_DIR」的既有不变量。③ `.bat` 记录真实 `%errorlevel%` 与自身路径，失败时记录 `bat skipped replacement`；成功路径的行为与顺序不变。④ 启动失败（DATA_DIR 被占用／不可用、不可变 Skill 初始化失败）在窗口化冻结构建下弹出可见对话框并写入 `<data>.startup-error.log`。⑤ 启动时若 journal 停在 installing，给出可见的一键恢复入口（启动已下载的新版本，否则给出明确手动指引）；其定位是**防止今后再次出现无声失败**——对 v0.6.9/v0.6.10 升级到本修复版这一次过渡，执行更新的仍是旧版本自己的更新器、修复版从未被启动，因此该恢复代码不会被触发，本次过渡只能由用户在发布说明指引下手动双击已下载的新 EXE 完成。单写者语义、占用检查、journal schema、锁 offset／length 与 v0.6.10 的「旧版本保留、不自动降级」全部未变，也不再删除任何正在运行的镜像。
- 按审批要求以**现代形态**恢复 v0.6.8 丢掉的三条语义：① 等待范围由单一 source PID 扩展到「安装目录内 `Code-v*.exe` 同镜像进程全部退出」（有界超时，默认 30 秒的独立常量），**不使用 taskkill 或按名/按镜像强杀**，超时后继续执行并把「等待超时 + 仍在运行的进程摘要」落盘；② 日志类操作改为 best-effort（`-ErrorAction Continue`），失败只记录、不阻断；③ 启动只以「替换文件存在且通过既有校验」为门（`$replacementReady`），校验之后的任何失败不再覆盖该决定，替换未就绪则响亮落盘（exit 23/24 及原因）。旧版本保留、不删除运行中镜像与单写者语义均保持不变。语义① 的意图来自 v0.6.7 更新器「先让同镜像进程收尾」，实现只做**有界等待、不做任何强制终止**，且超时必然继续，因此最坏只多等该常量，不引入新的挂起面（可用 `image_wait_timeout_seconds` 调低或置 0 关闭）。
- 隔离验收（真实生成的 PS／.bat，原始输出）：成功链路 exit 0，`update.log` 为 `update started → stage replace → stage verify → verified replacement ready; old versions retained → exit 0`，手递日志含全部 pre-lock 阶段与 `bat exit 0 script <bat>`，新版本被真实以 `--reuse-browser` 拉起（marker 写入），且该新进程**真实取得同一把数据目录 sidecar 锁**（marker 记录 `lock=acquired`，其后独立探测为 free，证明交接在启动新版本前已释放锁），旧镜像保留、成功路径自删保持不变；失败注入（partial 目标不可用）时两份日志均含 `EXCEPTION: System.IO.DirectoryNotFoundException: 未能找到路径中的某个部分。`、`SCRIPTSTACK: … 第 244 行` 与 `exit 24`，手递日志另含 `bat exit 24 script <bat>` 与 `bat skipped replacement`，**新版本未被误启动**；启动可见性（DATA_DIR 被占用）时出现标题为「Code 无法启动」的可见对话框（`FindWindowW` 取到句柄）并写入 `stage=startup code=data_dir_owner message=…`，进程退出码 1。
- 恢复路径安全加固：一次性过渡恢复此前直接用 journal 里的 descriptor 名称拼路径、并在用户点击后直接启动，缺少 descriptor 归一化、路径限定与文件校验（存在路径穿越与绕过下载信任链的风险）。现改为：journal 的 descriptor 必须通过既有 `_normalize_update_descriptor`（官方 https URL、名称恰为 `Code-v{version}.exe`、size 边界、64 位 hex digest）校验；候选名取自校验后的 descriptor，拒绝路径分隔符与 `..`；解析后的绝对路径必须仍在安装根内，并经 `_validate_safe_update_file` 拒绝符号链接、重解析点与多硬链接；只有同时通过 `_validate_completed_update_file`（size + sha256 + PE 身份）与 descriptor 一致性的候选才提供【确定】启动入口，否则只给手动指引，并把 `descriptor_invalid` / `verification_failed` 等拒绝原因落盘。八项隔离控制（1 项正控 + schema 不符／非官方 URL／名称不符／digest 非 64 位 hex／路径穿越／候选 digest 不符／候选 PE 身份不符）全部通过，全部负控均不弹启动对话框、不产生新进程。
